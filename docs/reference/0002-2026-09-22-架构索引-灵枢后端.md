## 1. 顶层布局

### 1.1 项目形态
- 单模块 Maven，`artifactId=lingshu`，parent `spring-boot-starter-parent:3.4.5`，`java.version=17`。无 Maven wrapper。
- 启动类 `LingShuApplication`：`@SpringBootApplication @EnableScheduling @MapperScan("com.onlyactwo.lingshu.mapper")`。
- 根目录：`pom.xml`、`CLAUDE.md`（项目约定）、`docs/`（INDEX + 业务背景 + 3 份规范；INDEX 引用的 `design/数据库.md`、`任务模块-*.md` 不在仓库）、`.claude/settings.local.json`（原作者 Mac 权限白名单，含明文 MySQL 密码命令）。

## 6. 横切机制

### 6.1 鉴权
- 登录：`AuthDomainServiceImpl.login` → `validateParam` → `selectByUsername` + `BCrypt.matches`（用户不存在与密码错同抛 `LOGIN_FAILED`）→ DISABLED 抛 `USER_DISABLED` → 读 `sys_config[jwt.secret]`、`[jwt.expireSeconds]` → `JwtUtil.generate`。
- 拦截器 `AuthInterceptor.preHandle`：无 `Bearer ` 前缀抛 `UNAUTHORIZED`；每次请求从 `sys_config` 读 `jwt.secret`（每请求一次 DB 查询）→ `JwtUtil.parse` → `UserContext.set(new UserInfo(userId, username, false))`；`afterCompletion` 清 ThreadLocal。**不检查用户是否已被禁用**（禁用只在登录时生效）。
- 当前用户：Controller 用 `UserContext.get()` 取 `userId/username` 塞进 DomainRequest 的 `operatorId/operator`。
- 角色判定（全部在领域层，按 DB 实时查）：`checkIsSystemAdmin(operatorId)` 查 `sys_user.is_system_admin`；`checkIsLabelAdmin(workspaceId,userId)` 查 `user_workspace_ship` role=3；组合 "系统管理员 或 空间 LABEL_ADMIN" 通过 try/catch `PERMISSION_DENIED` 实现。LABELER/REVIEWER 角色只在 createCase 校验成员时使用，任务操作接口不校验。
- MQ 消费者与定时任务把 `UserContext` 设为 `SYSTEM_MQ_CONSUMER`；回收 operator 为 `SYSTEM_AUTO_RECYCLE`；无 annotator 的 task 操作 operator 为 `SYSTEM`。
- CORS 全开（`*` + credentials）。无登录限流、无刷新/登出/黑名单。

### 6.2 响应包络
`LingShuServiceResponse.success(data)` / `.fail(code[,msg])`；分页 `LingShuServicePageResponse.success(list,total,pageNum,pageSize)`。Spring MVC 用默认 ObjectMapper（null 字段会输出）；`JsonUtil` 的 NON_NULL 只影响手动序列化（ext 入库、MQ 载荷）。

### 6.3 异常体系
`ErrorCode` 接口 → 各模块 `XxxErrorCode` 枚举 → `ServiceException.of(...)` → `GlobalExceptionHandler`（§4.3）。约定：业务拒绝直接抛不打日志；技术异常 `log.error` 后抛或吞；MQ 消费/AI/解析/导出全部"吞掉+记日志"。

### 6.4 事务边界
只有 6 处 `@Transactional(rollbackFor=Exception.class)`，全部通过 `@Lazy @Autowired private XxxImpl self` 自注入代理调用 public 事务方法：
- `DatasetDomainServiceImpl.saveDatasetWithInitialVersion`、`saveVersionAndBumpLatest`
- `CaseDomainServiceImpl.saveCaseGraph`（含 enqueueToPool，同一事务）
- `DispatchEngineImpl.enqueueToPool`、`moveTaskTx`（单条 task 移组）
- `TaskDomainServiceImpl.completeLabelTaskTx`、`submitReviewPassTx`、`submitReviewRejectTx`、`createResultVersionTx`

MQ 发送：submit 系列通过 `TransactionSynchronizationManager.registerSynchronization(afterCommit)` 放在提交后；createDataset/createCase/export 在事务方法返回后直接发。其他写操作（createUser/Workspace/LabelTool、addWorkspaceMember、saveTaskResult、autoRecycle、文件解析批量入库）无事务。

## 7. 核心业务流程（按代码追踪；M3 规则表的原始依据）

### 7.1 登录
`POST /api/auth/login` → `AuthDomainServiceImpl.login`：`validateParam`(空→INVALID_PARAM) → `authenticate`(selectByUsername；null 或 BCrypt 不匹配→LOGIN_FAILED；DISABLED→USER_DISABLED) → `generateToken` → `{token}`。

### 7.2 创建 Case（`CaseDomainServiceImpl.createCase`）
1. `requireManageableWorkspace(operatorId, spaceCode)`：空间不存在→WORKSPACE_NOT_FOUND；系统管理员放行，否则须该空间 LABEL_ADMIN。
2. `validateBasicParam`：name 1-255（流式模式 name+"_流式数据集" ≤128）、description ≤1024、dataSourceType、labelTool 非空。
3. `validateDataSourceAndResolveVersionId`：DATASET 模式必须传 datasetVersionId，版本存在、未删、`uploadStatus==READY`；STREAM 返回 null。
4. `ensureLabelToolExists`。
5. `validateTaskPlan`：stages 非空、type 非空、不重复、code 严格递增（顺序固定 aiPreLabel→label→aiPreReview→review→recheck，可裁剪）、至少含 aiPreLabel 或 label。Controller 已把 wire 的 `stage` 数字忽略、用 type 的 code 重写。
6. `validateAssignment`：对每个启用 stage：AI stage 需 `aiCode` 非空、preDispatchSize≥1(可空)、AiConfig 存在且 `labelToolCode==case.labelTool`；人工 stage 需 strategy 非空、STREAM 模式只允许 FCFS、members 非空、每个成员在空间且持有 `requiredRole`（LABEL→LABELER；REVIEW/RECHECK→REVIEWER）、FCFS 下 ratio 必须 null、FIXED_RATIO 下 active 成员 ratio 0-100 且和=100、至少一个 active。
7. 加锁 `case:create:{spaceCode}:{name}` → `ensureCaseNameAvailable`（同空间未删同名）→ STREAM 模式再查派生数据集名不重复。
8. `self.saveCaseGraph`（一个事务）：STREAM 模式先建 `lingshu_dataset(type=STREAM_ANNOTATION)` + version(READY, sampleCount 0)；`caseRepository.save`（status=RUNNING）；对每个启用 stage 建一个池 `label_task_group(type=stage.poolType, status=PENDING)`；DATASET 模式：取全部样本 id → `dispatchEngine.enqueueToPool(caseId, 首 stage.poolType, ids)`（同事务）。
9. `triggerInitialDispatch`：DATASET 模式事务提交后 `dispatchPool(caseId, 首池)`，失败仅 warn。STREAM 模式不派发（**代码里没有任何"流式推样本"的接口，流式模式实际不可用**）。
10. 返回 `{caseId}`。若首 stage 是 aiPreLabel，dispatchPool 会把题派给虚拟成员 aiCode 并发 `lingshu_task_dispatched` → AI 自动执行（§7.8）。

### 7.3 派发引擎（`DispatchEngineImpl`）
- 入池 `enqueueToPool(caseId, poolType, sampleIds)` [@Transactional，不加锁]：poolType ∈[2,6] 否则 POOL_TYPE_INVALID；case 存在且 RUNNING（否则 CASE_NOT_RUNNING）；空列表直接返回；`stage=fromPoolType`，`taskType=stage.code`；找池（无→POOL_NOT_FOUND）；`selectExistingSampleIds(caseId, taskType, ids)` 去重（幂等，等价于 uk_case_type_sample）；`seq=maxSeqInGroup(pool)+1…`；批量插入 task(status=1, round=1, taskGroupId=pool)；`increaseTotalCount(pool, n)`。
- `dispatchPool(caseId, poolType)`：锁 `dispatch:case:{caseId}:pool:{poolType}`（3s 等待，拿不到→OPERATION_CONFLICT）；`activeExecutors`：AI stage → `[aiCode]`；人工 → members 中 `active==null||active` 的 username；对每个 executor 调 `doDispatchToMember`。**不校验 case 是否 RUNNING**。
- `dispatchToMember(caseId, poolType, executor)`：同一把锁；单人补题。
- `doDispatchToMember`（无锁内部）：
  1. 解析配置：AI stage 要求 executor==aiCode 否则 EXECUTOR_INACTIVE；人工 stage 要求 executor 是 active 成员否则 EXECUTOR_INACTIVE；`preDispatchSize` 默认 3；取 strategy、ratio。
  2. 找池；`personalGroup=selectPersonalGroup(caseId, stage.code, executor)`；`inHand=countInHand(personalGroup)`(status 2/3/5)；`needCount=preDispatchSize-inHand`，≤0 返回（**预派发 = 始终把在手量补到 preDispatchSize**）。
  3. FIXED_RATIO：`total=datasetVersion.sampleCount`（流式为 0）；`memberLimit=total*ratio/100`；`assignedTotal=countByGroup(personalGroup)`（历史承接含已完成）；`needCount=min(needCount, memberLimit-assignedTotal)`，≤0 返回。FCFS 无上限。
  4. `takeFromPool(pool, needCount)`（status 1/5，按 seq 升序）；为空返回。
  5. 个人组不存在则 `createPersonalGroup`（type=1, stage, annotator=executor, name=`{caseName}-{executor}-{stageType}`, status=RUNNING）。
  6. 逐条 `self.moveTaskTx`（独立事务，条件更新 `task_group_id=pool AND status IN(1,5)`；affected=0 视为竞态跳过）：新 status = 原为 REWORK 则保持 5，否则 stage.code≤2 → LABELING(2)，否则 REVIEWING(3)；写 annotator、claimTime=now、新 seq。成功后立即发 `lingshu_task_dispatched`。
- 幂等/并发：入池靠 (caseId,taskType,dataSampleId) 去重；出池靠锁 + 条件更新。

### 7.4 领取 / 保存 / 提交标注
- 领取：没有独立"领取"接口。派发即领取（`claimTime` 在 moveToPersonalGroup 时写入）。标注员通过 `getMyTaskGroups` → `getTaskListInGroup` → `getTaskDetail` + `getSampleData` 获取工作。
- 保存 `saveTaskResult(taskId, sampleType, result)` → `writeResultSample`（无事务、不校验调用者、不校验 task 状态、不校验 result schema）：
  - ANNOTATION：`versionId=case.labelResultDatasetVersionId`，为空则 `getOrCreateResultVersion`（锁 `dataset_version:case:{id}:label_result` → double-check → `createResultVersionTx`：建 `lingshu_dataset(type=RESULT, name="结果集_case{caseId}", serviceObjName=labelToolCode)` + version(READY) + 回写 case 列）；`bizId=String(task.dataSampleId)`。
  - REVIEW：结果集必须已存在且能找到标注结果 sample（否则 LABEL_RESULT_NOT_FOUND）；`bizId=String(标注结果 sample.id)`。
  - 按 (versionId, bizId) 查：存在则 `updateSampleDataJson` 覆盖，否则 insert。**单 result 覆盖式，无版本历史**；同一 sample 的 review/recheck 结果互相覆盖。
- 提交标注 `submitLabelTask(taskId)`：task 存在；`taskType.isAnnotation()`（1/2）否则 TASK_TYPE_INVALID；status==DONE→TASK_ALREADY_COMPLETED；标注结果 sample 必须存在（RESULT_SAMPLE_NOT_FOUND）；`nextStage=nextStageInPlan(plan, current)`；`completeLabelTaskTx`：`updateToCompleted`（status=4, costTime=now-claimTime, operator=annotator；affected=0→TASK_ALREADY_COMPLETED）；afterCommit：发 `lingshu_task_completed{…,nextStageType}` + `dispatchToMemberQuietly(caseId, currentStage, annotator)`（给提交者补一题，异常吞）。**不校验 task 处于 LABELING/REWORK，也不校验提交者是 annotator**。

### 7.5 审核通过 / 驳回（`submitReviewTask`）
- 前置：task 存在；`!isAnnotation()`（3/4/5）；未 DONE；`currentStage=fromCode(taskType)`。
- PASS → `submitReviewPassTx`：`writeResultSample(REVIEW, {reviewAction:1, reviewComment})` → `completeTaskOrThrow` → afterCommit：发 task_completed（nextStage 可能为 null=末阶段）+ 给审核员补题。
- REJECT：`prevStage=prevStageInPlan`（无→PREVIOUS_STAGE_NOT_FOUND）；`target=selectByCaseTypeAndSample(caseId, prevStage.code, dataSampleId)`（无→REJECT_TARGET_NOT_FOUND）；`originActive=isExecutorActiveInStage(assignment, prevStage, target.annotator)`；`submitReviewRejectTx`：写质检结果(reviewAction 0) → 当前 review task 置 DONE → 上一阶段 task：
  - 原执行者仍 active：`rejectKeepInGroup(target)`：status=5(REWORK)、round+1，留在原个人组、annotator 不变（`claimTime` 不变，自动回收超时按最初领取时间算）。
  - 原执行者已 inactive：`rejectToPool(target, prevPool)`：status=5、round+1、改到上一阶段池、清 annotator/claimTime；afterCommit `dispatchPoolQuietly(prevStage)`。
  - afterCommit 再给审核员补题。
- **重要缺陷**：驳回不发 task_completed；被驳回 task 重做完成再次 submitLabelTask 时发 task_completed → 下一阶段 `enqueueToPool` 因去重不会新建 task（该 sample 的 review task 已 DONE），流程到此终止。即"打回重标→再次质检"链路**不会自动生成第二轮质检任务**。若 prevStage 是 aiPreLabel，驳回 target 是 AI task，原 aiCode active 时仅置 5 且不重新触发 AI。**TS 重写必须修：驳回后当前 review task 应回到可再次审核的状态，或重做完成后重新入池上一审核阶段（round+1 作为幂等键一部分）。**

### 7.6 `task-completed` 推进下一阶段
`TaskCompletedConsumer.onMessage`：`nextStageType==null` → ack；否则 `poolType=fromType(next).poolType` → `enqueueToPool(caseId, poolType, [dataSampleId])`（case 非 RUNNING 会抛→MQ 重试）→ `dispatchPool(caseId, poolType)`。

### 7.7 自动回收（`autoRecycleOverdueTasks`）
每分钟：`selectAutoRecycleCandidates(500)`（运行中 case、个人组、status 2/3/5、claim_time 非空、claim_time 升序）→ 对每条：读 case；`recycleMinutes=assignment.autoRecycleMinutesOf(stage)`，null 或未超时（`now-claimTime < minutes*60000`）跳过；找该 stage 池；`recycleToPool`（status 5 保留否则 1，清 annotator/claimTime，round 不变）；affected=0 跳过；记录 (caseId, poolType) → 循环结束后对每个组合 `dispatchPool`（异常吞）。AI stage 也适用。

### 7.8 AI 执行器（`AiTaskExecutorImpl.execute(taskId)`）
触发：`lingshu_task_dispatched` 且 taskType ∈{1,3}。步骤：task 存在且 AI 类型；case 存在；`aiCode=assignment.aiConfigOf(stage).aiCode`；`AiConfigDO=getAiConfigByCode`；源 sample=`selectById(task.dataSampleId)`。
- AI 预标(1)：`messages=[system(prompt), user(JSON(sampleDataJson))]` → LLM → 去 ``` 围栏 → JSON 解析 → `saveTaskResult(ANNOTATION, parsed)` → `submitLabelTask(taskId)`（走 §7.4 全流程）。
- AI 预审(3)：先按 `(case.labelResultDatasetVersionId, bizId=String(dataSampleId))` 找标注结果 sample；`user = {"inputData": 源样本, "labelResult": 标注结果}`；期望 LLM 输出顶层 `{reviewAction:0|1, reviewComment}`；否则 `submitReviewTask`（走 §7.5，包括驳回逻辑）。
- 所有失败：`log.error` 后 return，**task 停留在 LABELING/REVIEWING**，只能靠 autoRecycleMinutes 回收重派。无重试、无失败记录。规划 0002 M3 改为 `label_task.ext.aiFailure` + 瞬时错误重试 3 次。

### 7.9 导出（`exportCaseResult`）
触发端：format ∈{csv,jsonl}；case 存在；系统管理员或空间 LABEL_ADMIN；`updateExt(CaseExt{lastExport{EXPORTING, format, triggerTime}})`（整段覆盖）；发 `lingshu_case_export`。
消费端 `CaseExportDomainServiceImpl.exportCaseResult`：`countByVersionId(datasetVersionId) > 200000` → 失败；游标分页（500/批）拉源样本；每批取标注结果（bizId=String(src.id)），再取质检结果（bizId=String(label.id)）；渲染 CSV（UTF-8 BOM + 列 `caseId,bizId,sourceSampleId,inputData,labelResultId,labelResult,reviewResultId,reviewResult`，JSON 字段序列化为字符串，RFC4180 转义）或 JSONL（每行同名字段对象）；整体拼 `StringBuilder` 后 `putObject`；`downloadUrl=getPublicDownloadUrl`；回写 `ext.lastExport{DONE, objectKey, downloadUrl, finishTime}`；异常 → `{FAILED, failureReason(≤1024)}`。

### 7.10 数据集上传与解析
1. `getUploadPreSignedUrl{fileName}` → key `dataset/{日期}/{uuid}{后缀}` → `preSignedPutUrl(key, 3600)` → 前端 PUT 直传。
2. `createDataset`（校验 name 4-32、desc ≤512、ossPath 必填、labelToolCode 存在、权限、锁+同名查重）→ 事务建 dataset(type=ANNOTATION, latestVersionNumber=1) + version(versionNumber=1, uploadStatus=PARSING) → 发 `lingshu_dataset_version_parse{versionId}`。`createDatasetVersion` 类似（锁内重读 latest+1）。
3. `parseDatasetVersion`：version 存在 → dataset 存在 → labelTool 及其 `labelToolJsonSchema` 非空（否则 LABEL_TOOL_SCHEMA_MISSING）→ `FileTypeEnum.fromOssPath`（**仅 `.jsonl`**）→ `deleteByVersionId` 物理清场（重解析幂等）→ `getObject` 全量读入内存 → `compile(labelToolJsonSchema)`（Draft-07）→ 逐行：空行跳过，非法 JSON/非对象 → `recordParseError`；对象 → schema 校验失败则 skip（错误≤100 条记 rowNumber+前 3 条消息），通过则构造 sample（bizId=content.bizId 或 null）入批，满 1000 条 `batchInsert`（非事务）→ `updateParseResult(READY, sampleCount=successCount, ext=统计)`；任何异常 → `PARSE_FAILED` + `ext.parseFailureReason`。
4. **schema 语义**：`labelToolJsonSchema` 描述的是源样本格式（不是标注结果格式）；标注/质检结果不做 schema 校验。

### 7.11 其他
- `getCaseDetail.stageProgress`：按 plan 顺序，`aggregateProgress` 分组：DONE→done；池组且 status∈{1,5}→poolPending；个人组且 status∈{2,3,5}→personalDoing。
- `getMyContribution`：`aggregateByAnnotator` + scope + 两种通过率 + 近 30 天按天完成数；`submissionCount = cnt + reboundCnt`；`avgCostMillis = doneCostSum/doneCount`。

## 9. 疑点 / 坑（TS 重写时逐条决定沿用或修正）

1. 明文凭据：`application.yml` 默认 MySQL/Redis 密码；`SystemAdminInitTest` 硬编码 `admin/admin`；AI apiKey、TOS AK/SK 明文存 `sys_config`。→ 重写：全部走 `.env`，apiKey AES-256-GCM。
2. JDK 17（非 21）。
3. HTTP 状态恒 200。→ 重写：UNAUTHORIZED→401，其余按规划 0002。
4. 鉴权粒度粗：`/api/task/*` 不校验调用者是否为 task.annotator；`getCaseList/getCaseDetail` 不校验空间成员；`getTaskListInGroup` 任何人可看任何组；`getUploadPreSignedUrl` 任何登录用户可用。→ 重写：至少校验 annotator 与空间成员。
5. 每请求查库读 jwt.secret；配置无缓存。→ 重写：进程内缓存 + 变更失效。
6. 未使用代码：`UserContext.isSystemAdmin`、`CasePO.version`、`PageRequest`、`LockUtil.executeWithLock`、`CommonErrorCode.NOT_FOUND/FORBIDDEN/TOO_MANY_REQUESTS`、validation starter。
7. `label_task.biz_id` 永远为 null；`getTaskDetail/getTaskListInGroup` 返回的 `bizId` 恒 null，前端应用 `getSampleData.bizId`。→ 重写：创建 task 时填 bizId。
8. Case 状态机缺失：无启动/暂停/结束/删除接口；`TaskGroup.status/doneCount/costTime` 从不更新。→ M5 补。
9. 流式模式（STREAM）无推样本接口。→ 重写：M3 不实现 STREAM，创建时拒绝或保留占位。
10. 驳回后二次质检不会自动产生（§7.5）；驳回保留在原组时 `claimTime` 不重置。→ 重写必须修。
11. AI 失败无重试且任务卡在 in-hand；AI 输出无 schema 校验直接落库。→ M3 修。
12. 导出/解析全量进内存（上限 20 万行）。→ 重写：流式读写。
13. `dispatchPool` 不检查 case RUNNING；`takeFromPool` 无行锁。→ 重写：`SELECT ... FOR UPDATE SKIP LOCKED` + 检查 RUNNING。
14. FIXED_RATIO 用 `datasetVersion.sampleCount` 做总量，REWORK 也计入 `countByGroup`，配额会被打回题吃掉。
15. `DATASET_NAME_MAX_LENGTH` 32 vs 128 两处口径不一致。
16. CORS 全开 + allowCredentials。
17. docs 缺失（`数据库.md`、`任务模块-*.md`、`DEPLOY.md`），DDL 需从 PO 反推。
18. 无 SQL 迁移脚本、无 Flyway；`sys_config` 种子需手工。
