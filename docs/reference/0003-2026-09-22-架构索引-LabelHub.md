### 2.3 Socket.IO（`services/notificationService.js`，path `/socket.io/`）
- 握手鉴权：`handshake.auth.token` / `query.token` / Bearer；`decodeToken` 失败 → `next(Error)`；无 token 允许匿名。`REDIS_URL` 存在时启用 redis-adapter。
- 连接后自动加入房间：`user:{id}`、`user:username:{username}`、`role:{role}`、`task:{taskId}`。
- 客户端→服务端：`join:task`、`leave:task`、`notification:read(id)`、`notification:read_all`、`notification:unread_count`。服务端→客户端：`notification`、`notification:read_ack`、`notification:read_all_ack`、`notification:unread_count_response`。
- 通知类型：review_approved、review_rejected、ai_review_complete、task_assigned、task_unassigned、task_submitted、task_resubmitted、task_status_changed、task_due_soon、owner_message。角色可见性 `ROLE_VISIBLE_TYPES`。
- 可靠性模型（无 outbox 表）：`notifyUsersByUsername()` 先逐条 `db.insertNotification()` 再 `io.to(room).emit`；客户端每次 `connect` 都 `fetchNotifications()` 用 REST 全量对账。**markflow重写不用 Socket.IO，M5 采用轮询铃铛，只借鉴"先落库后推送"与类型/优先级设计。**

### 2.5 关键业务逻辑定位
- 状态机：`constants/statusMachine.js`；前端镜像 `src/types/index.ts STATUS_TRANSITIONS`。
- 并发：乐观锁 version（409）；悲观锁 lockedBy/lockedAt 30min（423）；`cleanupExpiredLocks` 每 60s。
- 时效：`utils/itemTimeliness.js` + `services/timelinessReminderService.js`（5min 扫描）+ `routes/tasks.js normalizeTimeliness`。**注意：只处理"到期结束/超时释放"，`*DueSoonNotifiedAt` 列存在但没有提前预警发送逻辑**（前端 `taskTimeliness.ts` 仅做展示等级）。

## 8. 移植时需注意的坑
1. `db_pg.js` 的"同步外观"靠启动预热内存缓存，写操作 fire-and-forget；生产实际只用 SQLite。markflow重写不复用任何 store 层代码。
2. `crudFactory` 带 `filterList` 时 `getAll` 后内存过滤/分页；不要搬。
3. 前端 token 同时存 localStorage 并以 Bearer 发送，cookie 只是后端另一路。
4. `createUserSchema`(zod) 允许 `admin`，但 `routes/users.js VALID_ROLES` 不含 admin；前端 `UserManage` 创建管理员会被后端拒绝。
5. `server/README.md` 与 `docs/DOC.md` 部分数字/路径已过期，以代码为准。
6. `gen-test-data.mjs` 输出路径硬编码。
