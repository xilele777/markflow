## 1. 结论速览

**一句话：markflow的"设计力"显著强于 LabelHub，LabelHub 的"工程力"显著强于markflow；两者强项弱项几乎完全互补，这决定了迁移方向。**

- **markflow质量定性**：架构与业务建模很强（多池派发引擎、AI 一等公民、数据资产层、多租户 RBAC、DDD 五层落地干净、后端 43 个测试类），代码本身写得认真；但**不可复现**（无 DDL / 无容器 / 无 CI）、**有真实安全隐患**（口令硬编码、CORS 全开带凭据、登录零限流）、**前端零测试**。它停留在"能被演示"，还没到"能被复现、被运维"。
- **LabelHub 短板定性**：工程执行成熟（CI 四门禁 + CD 自动回滚、WAL 备份、限流安全头、性能治理 -81%、真实跑了一年），但**业务模型已封顶**——"AI 预审"是 6 条硬编码规则（不是 AI）、流程是写死的线性状态机、SQLite 单文件 + 无 MQ，撑不起 AI 原生 / 流式 / 多租户。

**迁移推荐：以markflow为基座，把 LabelHub 的工程能力移植过去（补外围），而非反过来（重写核心）。** 详见 §7。

## 3. markflow质量详评：优势（含源码证据）

以下每条都在源码里核实过，不是 PPT 架构。

### 3.1 多池流水线 + DispatchEngine 派发引擎 —— 最核心优势

markflow把"流程"和"人"彻底解耦成两层：任务在哪个阶段（池）与谁来做（个人任务组）是两件独立的事。

- **流程可裁剪**：`StageTypeEnum`（[StageTypeEnum.java](../../submission/markflow-后端/src/main/java/com/onlyactwo/markflow/domain/task/model/StageTypeEnum.java)）定义 5 阶段 `AI_PRE_LABEL(1) / LABEL(2) / AI_PRE_REVIEW(3) / REVIEW(4) / RECHECK(5)`，每项带 `code`（task.task_type）、`poolType`（对应池 group.type）、`requiredRole`（人工阶段所需空间角色，AI 阶段为 null）。
- **编排校验极宽**：`CaseDomainServiceImpl.validateTaskPlan()`（[CaseDomainServiceImpl.java:428](../../submission/markflow-后端/src/main/java/com/onlyactwo/markflow/domain/task/service/impl/CaseDomainServiceImpl.java#L428)）只校验"顺序单调递增 + 去重 + 至少含 AI_PRE_LABEL 或 LABEL"。意味着**任意子集、任意组合都能跑**；新增节点 = 加一个枚举 + 建一个池，不动流转代码。
- **派发策略独立可扩展**：`StrategyEnum` 的 `FCFS`（先到先得）/ `FIXED_RATIO`（固定比例）在 [DispatchEngineImpl.java:150-180](../../submission/markflow-后端/src/main/java/com/onlyactwo/markflow/domain/task/service/impl/DispatchEngineImpl.java#L150) 独立分支；流式数据源强制 FCFS（[CaseDomainServiceImpl.java:519](../../submission/markflow-后端/src/main/java/com/onlyactwo/markflow/domain/task/service/impl/CaseDomainServiceImpl.java#L519)）。加"按技能/正确率加权"只需在策略层加一个实现。

**为什么这是压倒性优势**：标注平台的核心竞争力不是"能标"，而是"能把流程编排改掉而不动代码"。LabelHub 在这件事上是结构性受限的（见 §5-A2）。

### 3.2 AI 是真 AI，且 AI 是"一等公民"

- 真实 LLM 链路：`OpenAiCompatibleLlmClient`（JDK HttpClient，兼容 SSE，无状态，240 行）+ `LlmClient` 接口。
- AI 配置独立：`AiConfigDomainService` 管理算子（baseUrl/model/prompt/apiKey），apiKey 与业务配置隔离。
- **关键设计**：AI 通过订阅 `markflow_task_dispatched` 消息自动开工，完成后调用**与人完全相同**的 `submitLabelTask` / `submitReviewTask`（[AiTaskExecutorImpl.java](../../submission/markflow-后端/src/main/java/com/onlyactwo/markflow/domain/task/service/impl/AiTaskExecutorImpl.java)）。AI 在系统视角下就是"接单的人"。
- AI 预审输入设计严谨：user message 是 `{inputData: 源样本, labelResult: 待审标注结果}` 复合 JSON，通过 `(case.labelResultDatasetVersionId, bizId=String(task.dataSampleId))` 定位待审结果（[AiTaskExecutorImpl.java resolveLabelResultSample](../../submission/markflow-后端/src/main/java/com/onlyactwo/markflow/domain/task/service/impl/AiTaskExecutorImpl.java)）——注释明确写出"task.bizId 生产创建时不赋值，不能拿它做串联键"，说明作者真的踩过这个坑。
- LLM 输出做了 markdown 代码围栏剥离（`stripJsonFence`）——又一处实战细节。

**带来的能力**：AI 节点可插到任意阶段（预标/预审/二次复核），换个 prompt 就是新算子——因为 AI 走的是同一条池子 + 派发链路。LabelHub 做不到（§5-A1）。

### 3.3 有"数据资产层"，LabelHub 没有

markflow有完整三层实体 `DatasetDO → DatasetVersionDO → DatasetSampleDO`，并且：

- **预签名直传 TOS**：`getUploadPreSignedUrl` 接口，文件不过后端，前端直传对象存储。
- **异步解析**：`DatasetVersionParseConsumer` + `FileParserFactory`（JSONL），支持流式 + 分批，不阻塞 HTTP。
- **结果集也是数据集**：`DatasetTypeEnum.RESULT`，标注结果本身是一份可导出的版本化数据（通过 `getOrCreateResultVersion()` 惰性创建 + 分布式锁 double-check）。

**量级差距**：一个是"文件放进数据库"，一个是"数据资产平台"。LabelHub 的样本直接 JSON 进 `annotation_items.rawData`（§5-A5）。

### 3.4 有异步骨架（RocketMQ 4 Topic），且消费幂等是真的做了

| Topic | 驱动什么 |
|---|---|
| `markflow_task_dispatched` | 通知 AI 执行器；给业务方埋钩子 |
| `markflow_task_completed` | **驱动跨池流转**（流水线心跳）+ 结果回流 |
| `markflow_dataset_version_parse` | 异步解析文件 |
| `markflow_case_export` | 异步导出 CSV/JSONL |

- 发送侧用 `TransactionSynchronization.afterCommit` 在事务提交后发消息（[TaskDomainServiceImpl.java:236/343/366](../../submission/markflow-后端/src/main/java/com/onlyactwo/markflow/domain/task/service/impl/TaskDomainServiceImpl.java#L236)，`registerAfterCommit` 在 544 行）——避免"消息发了事务却回滚"。
- 消费侧幂等：`enqueueToPool` 按 `(caseId, taskType, dataSampleId)` 去重（[DispatchEngine.java:13](../../submission/markflow-后端/src/main/java/com/onlyactwo/markflow/domain/task/service/DispatchEngine.java#L13) + [TaskCompletedConsumer.java:20](../../submission/markflow-后端/src/main/java/com/onlyactwo/markflow/infrastructure/mq/consumer/TaskCompletedConsumer.java#L20)），异常上抛由 RocketMQ 重试。

**注意**：发送可靠性仍是"事务后发 + 失败仅记日志"的简化策略（见 §4-P1-8），不是完整 outbox。

### 3.5 多租户 / 三层权限

工作空间（Workspace）+ 空间成员 + 空间角色三层，角色含 SA（系统管理员，跨空间）/ LABEL_ADMIN / LABELER / REVIEWER（空间内可多角色）。`StageTypeEnum.requiredRole` 已把"人工阶段需要哪个空间角色"建模进枚举。LabelHub 只有 3 个全局角色（§5-A6）。

### 3.6 后端 43 个测试类，测的是业务规则

测试不是凑数，密度对 11 天产出的项目相当高。最大的几个：`CreateCaseDomainServiceTest` 558 行（Case 编排 + 全部校验分支）、`DispatchEngineImplTest` 474 行（派发引擎）、`GetMyContributionDomainServiceTest` 379 行、`GetTaskGroupListDomainServiceTest` 350 行，还有消费端 `TaskCompletedConsumerTest` / `TaskDispatchDomainMessageConsumerTest`。测试代码 8,783 行，约为后端主代码的 58%。

### 3.7 工程规范文档化程度高（写给 AI/新人的红线）

`docs/standards/` 三篇强规范（ddd-layering 12 条红线 + 12 项检查清单 / error-logging / naming-field），且**源码里能验证为真**：抽查 `TaskController` 确实手工做 DTO↔DO 转换、绝不直调 Mapper，与红线一致。

### 3.8 标注工具双模式统一架构

- **BUILTIN · Puck 可视化搭建**：18 个组件（实测 `puck/components/`：TextView/ImageView/VideoView/AudioView/CarouselView/RadioInput/CheckboxInput/SelectInput/RateInput/SegmentInput/BooleanInput/TextInput/Tabs/Row/Section/Divider/Spacer/SaveResultButton），含视频/音频——这是 AIGC 图生视频审核场景的前提。
- **IFRAME · 外部页面接入**：填 URL 即可，外部页面通过 `getSampleData / saveTaskResult / submitLabelTask` 通信。
- 两种模式对标注员都是"全屏 iframe + 队列 + 自动跳下一题"，体验一致。

## 6. LabelHub 值得保留的工程资产

LabelHub 真正的价值在**工程执行与生产运维**，这些恰恰是markflow缺的。以实测证据为准：

1. **CI 四道门禁 + CD 自动回滚**（[ci.yml](../../LabelHub/.github/workflows/ci.yml)）：lint → typecheck → e2e → build(+bundle 体积预算) → deploy。deploy 用 releases 符号链接 + 原子切换 + 健康检查 + **失败自动回滚**（[activate.sh:70-87](../../LabelHub/scripts/activate.sh#L70)：冒烟失败自动切回上一版并重验）。这是markflow最需要补的。
2. **前端性能治理闭环**：[check-bundle-size.cjs](../../LabelHub/scripts/check-bundle-size.cjs) 设了量化预算（入口预加载 gzip < 160kB、单 chunk < 200kB）并接入 CI 门禁；[webVitals.ts](../../LabelHub/src/services/webVitals.ts) 上报 LCP/INP/CLS/FCP/TTFB 五项。入口 gzip 从 Vue 版 306kB raw 一路压到预算线内。
3. **安全加固到位**（[index.js:84-94](../../LabelHub/server/index.js#L84)）：中间件链 `requestId → requestLogger → compression → cookieParser → securityHeaders → globalLimiter → cors → response → json(10mb) → auth`，限流 + 安全头 + 请求 ID + 全局限流都真实挂上。
4. **可观测性**：prom-client 指标（`metricsMiddleware` + `/api/metrics`）+ swagger 接口文档（`/api/docs.json`）。
5. **生产运维经验**（[DEPLOY.md](../../LabelHub/DEPLOY.md)，11KB）：WAL 感知备份（`VACUUM INTO` 单文件一致性快照）、Nginx 网关、密钥不进 env 块避免被 `pm2 save` 明文落盘、fail2ban、非 root deploy 用户、专用 ed25519——真金白银踩坑记录。
6. **前端测试文化**：Vitest + Testing Library，14 文件 83 用例（store/hook/工具/冒烟均衡覆盖）。
7. **工程纪律**：husky + lint-staged（提交前 eslint --fix + prettier）、editorconfig、prettier 全仓统一。

## 7. 迁移评估：三条路线对比与推荐

### 推荐：以markflow为基座，把 LabelHub 的工程能力移植过去

**核心判断：迁移成本不对称。**

- 把markflow的"多池派发引擎 + 数据资产层 + MQ + 多租户 RBAC"移植到 LabelHub，等于**重写 LabelHub 的后端核心**：状态机 → 派发引擎是范式切换，SQLite → MySQL+MQ 是基础设施切换，还要迁移线上 SQLite 数据。工作量 ≈ 重做一遍markflow后端。
- 把 LabelHub 的工程能力（CI/CD、容器化、限流、安全、监控、前端测试）移植到markflow，是**给已有强骨架补外围**——不动它的架构，只加护栏。性价比高得多。

### 三条路线对比

| 路线 | 做什么 | 工作量 | 风险 | 适合 |
|---|---|---|---|---|
| **A. markflow为基座 + 移植 LabelHub 工程力**（推荐） | 给markflow补：①可复现三件套（docker-compose + schema.sql/Flyway + CI）②安全加固（收口 CORS/鉴权旁路/限流/密钥外置）③前端测试 + 性能监控 ④补回缺失的 4 篇设计文档 | **中**（约 1–2 周），且全是"加法"，不动架构 | 低：不触碰markflow核心逻辑 | 想让项目进入"可复现/可运维/能演示 AI 原生"的状态 |
| B. LabelHub 为基座 + 移植markflow架构 | 重写 LabelHub 后端为派发引擎 + 资产层 + MQ + RBAC；迁移线上 SQLite 数据到 MySQL | **大**（等于重做后端） | 高：线上实例 + 数据迁移 + Node→Java 栈切换 | 仅当必须保住 LabelHub 线上实例和 Node 栈 |
| C. 合并各取所长 | 重做前后端 | **最大** | 最高：无清晰收益，两头都不靠 | 不推荐 |

### 若走 A，LabelHub 值得"搬进markflow"的清单（工程与体验资产，而非业务代码）

| 优先级 | 搬什么 | 搬到markflow的形态 |
|---|---|---|
| 高 | CI/CD 管线（ci.yml 四门禁 + 自动回滚思路） | 改成 `mvn test` + `tsc --noEmit` + `eslint` + 前端 vitest + 后端打包 + 部署回滚 |
| 高 | 可复现三件套 | 新增 `docker-compose.yml`（MySQL8 + Redis + RocketMQ）+ 从 mapper XML/PO 反推 `schema.sql`（或 Flyway）+ 最小 CI |
| 高 | 安全加固清单（限流/安全头/zod 校验） | 治markflow P0：CorsConfig 收窄、WebMvcConfig 鉴权旁路收窄到 `/api/auth/login`、加登录限流、密钥外置 |
| 中 | 前端性能治理（体积预算 + web-vitals + 错误上报） | markflow前端接入 `rollup-plugin-visualizer` + 预算门禁 + web-vitals |
| 中 | 前端测试文化（Vitest + Testing Library） | markflow前端补 vitest + 关键模块 smoke（http 层/permissions/表单校验） |
| 中 | 生产运维手册（DEPLOY.md 经验） | 移植备份/网关/密钥管理/fail2ban 到markflow部署 |
| 低 | 组件拆分实践 | 拆解markflow大页面（CaseNewPage 753 行等） |
| 不搬 | 双数据库实现（db_sqlite/db_pg）、SQLite、Socket.IO 通知 | markflow用 MySQL 单点反而干净；MQ 已覆盖异步，Socket.IO 可选不紧急 |
