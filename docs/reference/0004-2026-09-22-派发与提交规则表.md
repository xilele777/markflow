## 0. 名词与编码

| 名词 | 含义 |
|---|---|
| stage | 流程阶段，配置串 camelCase：aiPreLabel(1) → label(2) → aiPreReview(3) → review(4) → recheck(5)。`code` 同时是 `label_task.task_type` 与 `label_task_group.stage`；对应池 `type` = code+1（2–6） |
| 池 | `label_task_group.type ∈ 2..6`，每个启用 stage 一个，`annotator` 为 null，建 case 时创建，`status=PENDING` |
| 个人组 | `label_task_group.type=1`，`(caseId, stage, annotator)` 唯一，首次派题时创建，`status=RUNNING`；AI 阶段的 annotator = aiCode |
| task 状态 | 1 待分配 / 2 标注中 / 3 质检中 / 4 已完成 / 5 打回重标。在手 = {2,3,5}；池内可派 = {1,5} |
| 幂等键 | `uk_task_case_type_sample(case_id, task_type, data_sample_id)`：一个样本在一个阶段永远只有一行 task |
| 结果样本 | 与源样本共用 `markflow_dataset_sample`。标注结果 `bizId = String(源 sample.id)`；质检结果 `bizId = String(标注结果 sample.id)`。覆盖式，无历史 |
| 系统操作人 | 无 annotator 的 task 操作记 `SYSTEM`；消费者 `SYSTEM_MQ_CONSUMER`；回收 `SYSTEM_AUTO_RECYCLE` |

## 3. 派发引擎

### 3.1 入池 `enqueueToPool(caseId, poolType, sampleIds)`（事务内，不加锁）

| # | 规则 |
|---|---|
| 3.1.1 | poolType ∉ [2,6] → POOL_TYPE_INVALID |
| 3.1.2 | case 不存在 → CASE_NOT_FOUND；非 RUNNING → CASE_NOT_RUNNING |
| 3.1.3 | 样本列表为空 → 直接返回 |
| 3.1.4 | 池不存在 → POOL_NOT_FOUND |
| 3.1.5 | 查已存在 `(caseId, taskType, sampleId)` 的 task；已存在且 **未完成** → 跳过（幂等，同 Java） |
| 3.1.6 | **TS 修正（§9.10）**：已存在且 **DONE** → 「重开」：status=1、round+1、移回本池、清 annotator/claimTime/costTime、seq=池 max+1。这是驳回重做后再次进入质检阶段的唯一途径 |
| 3.1.7 | 全新样本 → 批量插入：status=1、round=1、seq 从池 max+1 连续；**TS 修正（§9.7）**：`bizId` = 源样本的 bizId |
| 3.1.8 | 池 `totalCount += 新插入条数`（重开不计） |
| 3.1.9 | 唯一键冲突（并发插入同一样本）→ 视为已存在，静默 |

### 3.2 派发 `dispatchPool(caseId, poolType)` / `dispatchToMember(caseId, poolType, executor)`

| # | 规则 |
|---|---|
| 3.2.1 | poolType 校验同 3.1.1；锁 `dispatch:case:{caseId}:pool:{poolType}`（wait 3s / lease 30s），拿不到 → OPERATION_CONFLICT |
| 3.2.2 | case 不存在 → CASE_NOT_FOUND；**TS 修正（§9.13）**：非 RUNNING → CASE_NOT_RUNNING（Java 不查） |
| 3.2.3 | `dispatchPool` 的执行者集合：AI stage → `[aiCode]`；人工 → members 中 `active !== false` 的 username，按配置顺序逐个 `doDispatchToMember` |
| 3.2.4 | `doDispatchToMember`：AI stage 要求 executor == aiCode；人工 stage 要求 executor 是 active 成员；否则 EXECUTOR_INACTIVE |
| 3.2.5 | preDispatchSize 缺省 3；`inHand` = 个人组内 status∈{2,3,5} 数；`need = preDispatchSize − inHand`，≤0 返回（预派发 = 把在手量补满） |
| 3.2.6 | FIXED_RATIO：`total = datasetVersion.sampleCount`；`limit = floor(total × ratio / 100)`；`assigned` = 个人组内全部 task 数（含已完成）；`need = min(need, limit − assigned)`，≤0 返回。FCFS 无上限。同 Java（§9.14 沿用，见 §8） |
| 3.2.7 | **TS 修正（§9.13）**：在一个事务内 `SELECT … FROM label_task WHERE task_group_id=池 AND status IN (1,5) ORDER BY task_group_seq LIMIT need FOR UPDATE SKIP LOCKED`；为空则返回 |
| 3.2.8 | 个人组不存在则创建：type=1、stage、annotator=executor、name=`{caseName}-{executor}-{stageType}`、labelToolCode、status=RUNNING |
| 3.2.9 | 逐条移组（同一事务，条件更新 `task_group_id=池 AND status IN (1,5)`）：新 status = 原为 5 则保持 5，否则 stage code ≤ 2 → 2，否则 3；写 annotator、claimTime=now、seq=个人组 max+1 递增 |
| 3.2.10 | 每条成功移组写 outbox `task-dispatched{caseId, taskId, taskType, annotator, dataSampleId, dispatchTime}`；事务提交后投递 |

### 3.3 `task-dispatched` 消费者

| taskType | 处理 |
|---|---|
| 1 / 3（AI） | 调 AI 执行器（§6）。瞬时错误抛出让 BullMQ 重试（attempts 3，指数退避 5s）；永久错误记录后返回 |
| 2 / 4 / 5（人工） | 仅 info 日志（预留通知，M5） |
| 其它 | warn 并返回 |

## 5. 审核通过 / 驳回（`submitReviewTask`）

| # | 规则 |
|---|---|
| 5.1 | reviewAction 非 0/1 → REVIEW_ACTION_INVALID（边界）；task 不存在 → TASK_NOT_FOUND；taskType ∈ {1,2} → TASK_TYPE_INVALID；已完成 → TASK_ALREADY_COMPLETED；**TS 修正**：调用者必须是 annotator |
| 5.2 | PASS：事务内写质检结果 `{reviewAction:1, reviewComment}`（规则 4.3/4.4）→ 完成当前 task（4.6）→ outbox task-completed（nextStage 可为 null，即末阶段）→ 提交后补题 |
| 5.3 | REJECT：`prevStage` = plan 中前一阶段，无 → PREVIOUS_STAGE_NOT_FOUND；`target` = `(caseId, prevStage.code, dataSampleId)` 的 task，无 → REJECT_TARGET_NOT_FOUND |
| 5.4 | `originActive` = target.annotator 在 prevStage 仍 active（AI stage：== aiCode；人工：成员且 active !== false） |
| 5.5 | 事务：写质检结果 `{reviewAction:0, reviewComment}` → 完成当前 review task → 处理 target： |
| 5.5a | originActive：留在原个人组，status=5、round+1；**TS 修正（§9.10）**：`claimTime=now` 重置（Java 不重置，自动回收会按最初领取时间误算） |
| 5.5b | !originActive：退回 prevStage 池，status=5、round+1、清 annotator/claimTime；prevStage 池不存在 → POOL_NOT_FOUND |
| 5.6 | **TS 修正（§9.10）**：5.5a 且 prevStage 是 AI 阶段 → 写 outbox `task-dispatched`，让 AI 重新执行（Java 只置 5 不触发） |
| 5.7 | 提交后：5.5b 时 `dispatchPool(prevStage)`（quiet）；给审核员补题（quiet） |
| 5.8 | 驳回不发 task-completed（同 Java）；被驳回 task 重做完成后走 4.6 发 task-completed → 3.1.6 把已 DONE 的本阶段 review task 重开（round+1、回池）→ `dispatchPool` 再派 → 第二轮质检 |

## 9. 队列可靠性（TS 新增）

- 表 `mq_outbox(id, queue, job_name, job_id, payload jsonb, status, attempts, next_retry_time, last_error, create_time, update_time)`。
- 生产者在业务事务内插 outbox 行（PENDING）；事务提交后立即投递：`queue.add(job_name, payload, {jobId})` 成功即删行，失败记 `last_error`、`attempts+1`、`next_retry_time = now + 30s`。
- 重投定时器每 30s 扫 `status=PENDING AND next_retry_time <= now`（最多 100 条）再投递。
- `jobId`：dataset-parse 沿用 `version-{versionId}`；其余为 `outbox-{行 id}`（全局唯一，避免 removeOnFail 保留的失败记录让同 id 的新 job 被静默忽略）。
- 消费者全部幂等：入池去重、AI 执行器检查 task 状态、导出覆盖式写 ext。
