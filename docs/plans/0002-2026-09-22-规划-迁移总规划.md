## 0. 迁移全貌

迁移是四条线，不只是后端：

| 线 | 内容 | 来源 |
|---|---|---|
| A 后端 | 用 Node + TS 重写灵枢后端，接口契约与灵枢前端严格一致 | 灵枢 Java 源码作为规格 |
| B 前端 | 接管灵枢 React 18 前端，修其缺陷，补 LabelHub 的前端工程资产 | 灵枢前端 + LabelHub `src/` |
| C 功能补齐 | LabelHub 有而灵枢没有的业务能力 | 迁移报告 §4 差距矩阵 |
| D 上线 | 部署、监控、备份、切换、LabelHub 封存 | LabelHub `scripts/`、`DEPLOY.md` |

四条线交错推进，按里程碑组织；每个里程碑结束时前端可手工验证一段完整业务。

## 1. 不变量（契约来源）

- 接口路径/方法/字段：灵枢 `controller/*Controller.java` 及其 `request/`、`response/`；前端实际调用以 `src/features/*/api.ts` 为准（35 个接口）。
- 响应包络 `{success, code, message, data, timestamp}`；分页顶层加 `total/pageNum/pageSize`。
- 错误码字符串沿用灵枢各 `*ErrorCode.java` 的 `code`；HTTP 状态：UNAUTHORIZED→401、FORBIDDEN/PERMISSION_DENIED→403、TOO_MANY_REQUESTS→429，其余 200（前端 `http.ts` 已按此处理）。
- 枚举 code 值见快照 0001 §5；时间戳全部毫秒数字。
- 业务规则唯一规格：`domain/task/service/impl/{DispatchEngineImpl, TaskDomainServiceImpl, AiTaskExecutorImpl, CaseDomainServiceImpl, CaseExportDomainServiceImpl}.java`、`domain/dataset/service/impl/{DatasetDomainServiceImpl, FileParseDomainServiceImpl}.java`。
- 表结构：迁移报告附录 A 的 11 张表，改 PostgreSQL（`bigint` 毫秒、`jsonb`），新增表随里程碑追加迁移。

## 2. 技术栈（定）

- 后端 `F:/label/apps/server/`：Node 22+、TypeScript、Express 5、PostgreSQL 16 + Kysely（含 migrator）、Redis 7 + ioredis（锁/限流/登录失败计数）、BullMQ（四个队列：task-dispatched、task-completed、dataset-parse、case-export）、AWS SDK v3 S3（本地 MinIO，线上 MinIO 或火山 TOS S3 兼容端点）、jsonwebtoken、bcryptjs、zod（入参）、ajv（样本 schema）、pino、prom-client、vitest + supertest（连真实 pg/redis）。
- 前端 `F:/label/apps/web/`：保留灵枢栈（React 18、Vite 6、AntD 5、TanStack Query、Zustand、Puck）；新增 vitest + Testing Library + happy-dom、web-vitals、bundle 预算脚本。
- 本地：`deploy/docker-compose.yml` 起 pg/redis/minio 三件；无 RocketMQ、无 MySQL、无 JDK。
- 生产：单机 pm2（后端）+ Nginx（前端静态 + `/api` 反代）+ 系统级 pg/redis + MinIO 或 TOS；内存需求约 1.5 GB，现有 ECS 可承载。

## 3. 里程碑

### M0 骨架与登录（1–2 天）

- 后端脚手架：目录 `src/{app,modules,infra,db}`，包络/错误处理/鉴权中间件、pino 日志、zod 校验、配置全部来自 `.env`（无默认口令，缺失即退出）。
- compose + V1 迁移（11 张表）+ 首启引导（`jwt.secret`、`jwt.expireSeconds`、admin 从环境变量幂等写入）。
- 接口：`auth/login`、`user/getCurrentUser`。
- 前端：复制灵枢前端到 `lingshu-web`，`git remote rename origin upstream`；`LoginPage` 改用 `pickHomePath`（F17）。
- 验收：前端登录成功，按角色进入首页；`vitest` 对 login/getCurrentUser 的 supertest 测试通过。

### M1 主数据（2–3 天）

- 后端：workspace（创建、加成员、列表）、user（创建、列表、改密码、我的贡献）、labeltool（创建/更新/列表，schema 存 jsonb）、aiconfig（创建/更新/列表，apiKey 用 AES-256-GCM 加密存储，密钥来自 `LINGSHU_CONFIG_ENC_KEY`）、sys_config 读写。
- 前端：无改动。
- 验收：前端"系统"菜单四页与"我的贡献"页全通；每个模块有接口测试。

### M2 数据集（2–3 天）

- 后端：dataset/version/sample 接口；预签名 PUT 直传（MinIO CORS 放行前端来源）；`dataset-parse` worker：从对象存储拉文件，按 jsonl/csv 解析、ajv 按标注工具 schema 校验、分批写样本、更新 `upload_status`；样本预览接口。
- 前端：无改动。
- 验收：前端上传 jsonl → 版本 READY → 预览样本；错误文件 → PARSE_FAILED 且原因可见。

### M3 任务流水线（4–6 天，核心）

- 先写一份《派发与提交规则表》（新增文档），把 Java 三个 Impl 的每个分支翻成中文规则，再实现。
- 后端：case 创建（校验、建各阶段池、样本入首池、AI 阶段自动派发）、case 列表/详情、任务组列表；派发引擎（入池幂等键 `(caseId, taskType, dataSampleId)`、出池按 FCFS / FIXED_RATIO、Redis 锁 `dispatch:case:{caseId}:pool:{poolType}`、预派发数量、个人组创建与计数）；任务接口（组内列表、详情、样本、结果读写、提交标注、审核通过/驳回：驳回留组重做或退池）；`task-completed` 消费者推进下一阶段；自动回收定时任务；`task-dispatched` 消费者触发 AI 执行器（调用 LLM，写结果样本，走与人相同的提交路径；失败分类记录到 `label_task.ext.aiFailure`，瞬时错误重试 3 次）；`case-export` worker（CSV/JSONL 上传对象存储，写 `case.ext.lastExport`）。
- 队列可靠性：BullMQ 任务在事务提交后入队；入队失败落 `mq_outbox` 表由定时器重投。
- 前端：无改动。
- 验收：前端完整跑通"建 case（AI 预标 + 标注 + 审核）→ 标注员提交 → 审核通过/驳回 → 重标 → 导出下载"；一条 case 的端到端自动化测试通过。

## 5. 风险与对策

- **派发引擎翻译走样**：M3 先出规则表再编码；端到端测试覆盖通过/驳回/重标/AI 失败四条路径。
- **前端依赖 Java 序列化细节**：`JsonNode` 字段原样透传（pg `jsonb` → 直接返回）；ID 保持在 2^53 内（pg `bigint` 序列足够）。
- **BullMQ 与 RocketMQ 语义差异**：一队列一消费者组；消费者按幂等键去重；不依赖广播。
- **对象存储切换**：本地 MinIO、线上 TOS 走同一 S3 客户端，仅 endpoint/凭据不同；预签名 URL 必须是浏览器可达地址。
- **上下文丢失**：每里程碑必出快照；规则表、接口清单等中间产物都落文档。
