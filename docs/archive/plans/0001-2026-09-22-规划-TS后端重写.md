# 规划 0001 · 灵枢后端 TS 重写（一页纸）

日期：2026-09-22 ｜ 状态：已确认路线，未开工 ｜ 上一版：无 ｜ 对应快照：`docs/handoff/0001-*`

## 目标

用 Node.js + TypeScript 重写灵枢后端，实现与灵枢前端（`submission/lingshu-web-前端`）完全一致的接口契约，前端零改动即可运行；同时吸收 LabelHub 的工程资产（CI、部署、限流、指标、前端测试）。

## 不变量（契约来源）

| 项 | 以什么为准 |
|---|---|
| 接口路径、方法、入参出参字段 | Java `controller/*Controller.java` + `controller/request|response/*`；前端实际调用见 `src/features/*/api.ts`（35 个接口） |
| 响应包络 | `{success, code, message, data, timestamp}`；分页顶层加 `total/pageNum/pageSize` |
| 错误码字符串 | Java 各 `*ErrorCode.java` 的 `code` 值原样保留；HTTP 状态：UNAUTHORIZED→401、FORBIDDEN/PERMISSION_DENIED→403、TOO_MANY_REQUESTS→429，其余 200 |
| 枚举 code 值 | 见快照 0000 §6（TaskStatus/TaskType/TaskGroupType/CaseStatus/WorkspaceRole 等） |
| 业务规则 | Java `domain/task/service/impl/{DispatchEngineImpl,TaskDomainServiceImpl,AiTaskExecutorImpl}.java` 为唯一规格，翻译时逐分支核对 |
| 表结构 | `灵枢迁移报告与总体计划.md` 附录 A 的 11 张表，改为 PostgreSQL（`bigint` 时间戳毫秒、`jsonb`） |

## 技术栈（定）

Node 22+ · TypeScript · Express 5 · PostgreSQL 16 + Kysely（类型安全 SQL，迁移用 Kysely migrator）· Redis 7 + ioredis（锁、限流、登录失败计数）· BullMQ（替代 RocketMQ：派发通知、AI 执行、文件解析、导出四个队列）· AWS SDK v3 S3（MinIO 本地 / 火山 TOS S3 兼容端点线上）· jsonwebtoken · bcryptjs · ajv（样本 JSON Schema 校验）· zod（入参校验）· pino · vitest + supertest（对真实 pg/redis 跑）· prom-client。

仓库：`F:/label/lingshu-server/`（新建）；前端仍为 `F:/label/lingshu-web/`（从 submission 复制）。

## 风险

- 派发引擎与驳回分支翻译走样 → M3 先把 Java 三个 Impl 的分支翻成中文规则表（新增文档），再写代码。
- 前端某些字段依赖 Java 序列化细节（如 `JsonNode` 原样透传、`Long` 精度）→ 大 ID 用 `bigint` 转字符串前先确认前端类型（前端用 `number`，保持 pg `bigint` 在 2^53 内即可）。
- BullMQ 语义与 RocketMQ 不同（无 topic 广播）→ 每个原 topic 对应一个 queue，消费者幂等按 `(caseId, taskType, dataSampleId)`。
